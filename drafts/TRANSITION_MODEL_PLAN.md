# Модель перехода: план реализации (настоящий прогноз вместо повторения меню)

Статус: план, согласованный по сути (2026-09-27). Числа: γ = 0.8 за ход, ширина
луча B = 3, глубина H = 3. Работы входят как рёбра, **открывающие возможности**,
с измеренными эффектами. Скрытые клетки — среднее по **всем** раскрытым (завышение
ранней игры — стимул к разведке, а не изъян).

## Зачем

Нынешний поиск перебирает «сегодняшнее меню, повторённое N раз»: тот же список
кандидатов на каждом уровне, постоянные дельты, без дисконта. Он не может увидеть,
что действие **меняет набор возможностей** (основание города, раскрытие клетки,
рост, ход к площадке). Из-за этого, в частности, возникает замерзание: если все
сегодняшние дельты нулевые, цепочка нулей даёт ноль и агент бездействует всю игру.

Настоящий прогноз: в будущем состоянии **перевыводить** набор возможностей и
оценивать ветвь по индексу `Σ ln(DoF)` с дисконтом за ход.

## Архитектура

* **Python** разворачивает ветви и переходы (ценности площадок/городов/технологий
  живут здесь: они зависят от карты, тумана и модели мира).
* **Rust-ядро остаётся судьёй одного шага** и не меняется: вето Аксиомы 3, штраф за
  необратимость, правило «строго > 0», индекс. Это сохраняет аксиоматику в одном
  месте и не требует портировать оценки в Rust.

Модуль: `brain/forecast/` (новый), покрытый тестами рядом с существующими.

```
brain/forecast/state.py      — предсказанное состояние: сущности, города, раскрытое
brain/forecast/transitions.py— переход «действие → состояние'» по семействам
brain/forecast/options.py    — перевывод набора возможностей для состояния'
brain/forecast/search.py     — луч с дисконтом; оценка узла через ядро
```

## Переходы (что именно предсказываем)

| семейство | состояние после | ценность преемника |
|---|---|---|
| `goto`/`move`/`explore`, носитель | юнит на целевой клетке; раскрытие | ценность города на площадке (`_site_city_value`) + информация |
| `goto`/`move`, не носитель | юнит в новой точке; раскрытие | информация (сужение полосы) |
| `build_city`/`found_city` | носителя нет, есть город размера 1 | индекс с городом − носитель (формула города) |
| `research_tech` | появляется сущность технологии | `tech_research_gain` |
| `produce_<тип>` | через N ходов юнит | `unit_options(тип) × γ^N`, N = `turns_to_prod_complete` |
| работы (`irrigation`, `mine`, `road`, `cultivate`, `plant`, `transform_terrain`) | выход клетки/террейн изменился | **измеренная таблица эффектов** + открываемые возможности |

Ценность ветви: `ΔDoF(сейчас) + γ · max V(состояние')` — то есть «что откроется».
Дисконт применяется за каждый ход прогноза; при γ = 0.8 цепочка 5 шагов даёт 3.36
вместо 5.

## Измеренные числа для работ (на 2026-09-27)

| работа | до → после | Δ еда/щиты/торговля | n |
|---|---|---|---|
| `cultivate` | Forest(+Pheasant) → Swamp | 0 / −2 / 0 | 12 |
| `cultivate` | Swamp → Forest(+Pheasant) | 0 / +2 / 0 | 12 |
| `build_road` | Forest, Plains | 0 / 0 / 0; `goto` 8 → 8 (задержки 0–2 хода) | 5 |
| `irrigation`, `mine`, `plant`, `transform_terrain` | — | **в работе** (нужен подходящий террейн) | — |

Цепочка/открытие: строгое «до/после» после `cultivate` на Forest — **ничего не
открывается**; `build_road` **исчезает** из валидных после появления дороги.
Первая версия сводки объявила открытие ошибочно (не сравнивала с исходным
набором) — исправлено.

## Луч и цена

Луч B = 3 по оценке узла; глубина H = 3. Замер (`scripts/bench_lookahead.py`):
при узком луче прогноз дешевле нынешнего полного перемножения меню. Целевой бюджет
— не более ~50 мс на решение.

## Решающие тесты (заданы ДО реализации)

1. **Синтетика «идти → основать»**: поселенец, под ним площадка гейт не проходит,
   в трёх ходах — годная, все сегодняшние дельты нулевые → агент **идёт**.
2. **Живой прогон**: замерзаний (0 решений) — **ноль** у обеих сторон.
3. **Движение видно**: в решениях появляются семейства `goto`/`move`/`explore`.
4. **Если движения появятся, а счёт не вырастет — это результат**, и подаётся так.
5. Тесты ядра не трогаем: Rust-ядро остаётся тем же; его поведение проверяется
   существующими тестами плюс новыми на ветвление.

## Что НЕ делаем

* Не подбираем γ и W_INFO под счёт (γ — смысл «дальше дешевле», W_INFO — из замера
  разброса клеток на корпусе).
* Не ставим правдоподобные числа туда, где замер дал ноль: ноль остаётся нулём, и
  это пишется прямо.
* Не выдаём прогоны на старом движке за проверку DOF-Core (см. `runs_superseded/`).
